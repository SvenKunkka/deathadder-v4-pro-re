# 接收器互斥锁和优先级继承恢复

新增第 50 个 C11 单元，恢复 `0E06CDAC` 加锁、`0E06CEA8` 解锁、`0E06DFC8` 优先级调整，以及等待、超时后的恢复逻辑。另将真实锁函数接入存储启动与连续写入验证。本轮新增 **2,368 组原指令输入，全部通过**。

## 已恢复

- 空闲锁获取、同一线程递归加锁、计数回绕、零等待超时返回 -16。
- 竞争时按有符号优先级实施继承，下限 -127；重排就绪队列、登记等待线程和超时。
- 解锁时检查所有权，递归计数递减，恢复所有者原优先级，从等待队列取出线程、取消其超时并移交所有权。
- 等待返回失败后重算优先级；需要重新调度时保留后续返回阶段。
- CPU请求 `0E0611CC` 前精确停下，保存阶段和参数，不向调用者伪造已获取锁或已完成调度的结果。

`receiver_mutex.h` 的返回值区分“原函数已经返回”和“停在CPU请求前”，原固件返回值通过独立输出参数交付。续段接口要求调用者提供实际切换后的RAM、优先级和结果；接口本身不生成CPU切换。互斥锁的状态至少覆盖20字节；初始化函数写前16字节，加锁维护 +16 的原优先级字段。

## 原指令比较

[互斥锁比较](receiver-mutex-comparison.json)：**2,240组，208,008条原指令**。其中1,848组运行至原函数/续段返回，392组停在CPU请求入口：加锁296组、解锁交接32组、失败续段重新调度64组。覆盖返回0、-16、-22、-1、-11，保存优先级、链表、超时和所有权变更一致。

后续段从原 `0E06CE22/CE7E/CF04` 指令开始，使用显式输入的切换后状态；不能把这些独立续段当作已验证的自动CPU切换。比较完整128KiB RAM、4KiB RTC窗口、BASEPRI与停止参数；临时栈不纳入最终比较。

[存储启动中的真实锁](receiver-storage-mutex-comparison.json)：**128组，5,694,373条原指令**。原程序实际执行ready、分区查询、mount、映射读写和锁函数，187次加锁、187次解锁均通过；80组成功、48组按原路径拒绝。比较全部RAM、2MiB存储快照和优先级。此部分没有线程竞争，也没有预设成功的锁返回。

## 连续组合

[连续验证](receiver-mutex-storage-continuous-comparison.json)：193次存储启动、192个写入周期中，**1,924次锁操作均调用恢复后的逻辑**。384条配置读回、573次辅助键/删除检查通过，最终存储摘要与上一阶段一致。之前的外部固定成功锁回调已在这份测试中替换；旧报告保留原验证范围。

本轮按特权CPU、有效且有限的链表、静态RTC输入验证。无竞争的连续写入不代表竞争下完整系统运行；实际CPU切换、异常返回、跨核和无线空口行为仍未验证。库本身只操作调用者传入的内存，不写入实物设备。
