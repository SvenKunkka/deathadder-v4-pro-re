# mode4 特殊 `02 55 00` 帧：来源、生产条件与消费者

结论：这是一条明确构造出来的短帧，主要在内部 interval 参数为1、没有待发队列/缓存数据时使用。正常接收器消费者必然拒绝其附加校验，**不会用它刷新普通链路确认或失联计数**。发送侧“提前 TXEN，然后后续时槽只 START”的代码结构支持它是**提前准备发射端的占位帧**，但该用途仍属强推断，未测量射频状态与 ramp/PLL 时延。

本报告使用官方1.20的两端 RAM 镜像、最终反编译和GNU汇编；没有重复提取、运行固件、写设备或改既有模式4报告。逐文件hash、原始指令字节及原固件偏移见 `mode4-special-frame.json`。

## 一、确切原字节

鼠标 DMA TX buffer 为 `23002650`。

| RAM指令地址 | 原始机器字节（文件序） | 指令/作用 |
|---|---|---|
| `23024A28` | `45 F2 02 56` | `movw r6,0x5502` |
| `23024A34` | `00 22` | `movs r2,0` |
| `23024A3A` | `9A 70` | `strb r2,[r3,#2]`，把byte2置0 |
| `23024A42` | `1E 80` | `strh r6,[r3]`，小端写byte0=02、byte1=55 |
| `23024A44` | `C2 F8 D0 3E` | 写 `RADIO.PACKETPTR` |

因此有效 DMA 帧就是 `02 55 00`：第0字节长度2，随后两个payload字节。byte3仍可能保留旧值，但不在该声明长度范围内。它并非固件静态数据区中直接存放的三字节常量。

`23024A28` 对应鼠标 radio文件 offset `0x51C4`、flash `0x0E0711C4`。映射依据 `0E06C79C -> 23020000`；其余指令已记录在JSON。

此路径直接设置PACKETPTR，返回到调用者；不进入 `23024BAA` 的普通上行“负和校验+长度递增”。不得把它自动补成带校验帧来解释原固件。

## 二、构造与真正挂接发送的条件

以下条件针对 mode4 TX candidate handler 的slot0/3主路径，不能替代全部状态机。

1. 模式为4，软件radio状态 `23002A04==0x18`，handler事件参数3；否则该分支不处理。
2. 内部interval参数 `230029AC==1`，slot为0或3。
3. 缓存motion标记 `23002671==0`。
4. `230216B0(0)` 返回1，证明六个发送队列均空。
5. retry holdoff字节 `230029D0==0`。
6. 当前频道的计数 `230029D1[channel]`：连接状态 `23002794==3` 时必须 `<4`，其他状态必须 `<16`。

源码关联：`2302243C.c` 的 `LAB_23024C74 -> LAB_230249EE -> LAB_23024A06`；汇编 `23024C74..23024C82`、`230249EE..23024A16`、`23024E84`。达到频道计数阈值会绕过这条短帧路径，继续普通构造路径；在仍无队列数据时可落入 `17` 状态包，因此短帧不会永久替代带确认的状态包。

### 六个队列为空的证据

`230216B0` 比较 peer-context（stride `0xEE0`）中这两组各6个索引：

- write位置：`23002AD6..23002ADB`
- read位置：`23002ADC..23002AE1`

所有对应项相等才返回1。交叉验证：`230214E0` 仅在某对索引不相等时返回数据项；`2302145C` 弹出数据时推进第二组索引并按队列容量回绕。故这里不是比较设备ID或字节内容，而是检查队列空状态。检查是逐项进行的，没有据此声称是并发一致快照。

### 构造成功仍不等于已发送

写入短帧并配置订阅后读取 TIMER.CC7：

- slot0：CC7必须大于99。
- slot3：CC7必须小于或等于250。

门限失败时撤销TXEN订阅，软件状态留在idle `0x18`；成功才置TX `0x19`。因此观察到缓冲有 `02 55 00` 不能单独证明发生了RF发射。

## 三、为什么判断为发射准备占位帧

`23021800` 直接初始化DPPI映射，通道号在这一镜像中是确定的：

| DPPI通道 | 发布源 |
|---:|---|
| 0 | TIMER020 COMPARE0 |
| 1 | COMPARE1 |
| 2 | COMPARE2 |
| 3 | COMPARE3 |
| 4 | COMPARE4 |
| 5 | COMPARE5 |
| 6 | RADIO ADDRESS |

特殊帧slot0将TXEN订阅到通道0，slot3将TXEN订阅到通道2；两者仅 OR `READY_START`（SHORTS bit0）。同一 interval1 调度中，后续slot1/4的普通数据构造使用 `SUBSCRIBE_START` 接到通道2，而不是再次TXEN。对应已恢复的原始鼠标tick：

| 半周期 | 特殊帧准备 | 特殊帧TXEN事件 | 后续普通数据准备 | 普通START事件 |
|---|---:|---:|---:|---:|
| 第一段 | 前周期CC1=470，slot0 | 下一COMPARE0=500/清零边界 | CC1=75，slot1 | COMPARE2=100 |
| 第二段 | CC1=220，slot3 | COMPARE2=250 | CC1=325，slot4 | COMPARE2=350 |

这些是硬件任务触发值，**不是实测空口包起止时间**。若后续仍无队列数据，slot1/4可直接返回而不发送普通包。

鼠标 `23021704` 的mode4 END处理只把软件TX `0x19` 改为idle `0x18`，该END分支没有执行DISABLE。特殊帧构造没有新增PHYEND_DISABLE；模式初始化 `23025778` 将SHORTS清零后设置READY_START，RX结束路径清除PHYEND_DISABLE。结合后续START-only路径，可以合理推断它让射频发射流程先就绪，为稍后可能到达的普通数据节省重新TXEN的准备步骤。

**限制：** 特殊帧分支执行的是 `SHORTS |= 1`，会保留已有其他位；不能仅凭该分支声称所有可能入口的PHYEND_DISABLE都已清除。硬件是否处于TXIDLE、节省多少时间/功耗、厂商是否称它为dummy/warm-up，尚无实机状态轨迹或厂商符号佐证。报告采用“发射准备占位帧”作为解释性命名。

## 四、接收器实际怎么处理

正常mode4 IRQ路径完全可追踪：

`23020A00: RADIO.END -> 23024190(4) -> state0xC -> CRCOK/length -> extra checksum`

对于长度2、数据 `55 00`：

- 硬件CRC不通过：直接拒绝。
- 硬件CRC通过：软件将length减1，数据求和只含 `55`，期望负和为 `AB`；接收到的末字节为 `00`，不相等。
- `230242BC` 条件分支跳至 `2302420A`：清RX长度，随后将软件接收状态设为 `0xB`。
- 不执行后面的有效包复制、sequence更新、miss counter重置或 `23021C24` 数据通知。
- 本次检查的mode4 IRQ及此消费者路径中没有 `55` 的例外判定；不能因此断言所有诊断/异常状态代码中也绝无其他用途。

接收器 `23023FA4` 在RX slot0/3设置 `END_START`（SHORTS bit5），清PHYEND_DISABLE（bit19）。所以**应用校验拒绝不等于硬件没有接收事件**；硬件END仍能经shortcut触发下一次START。随后 `230240AC(4)` 可以把软件 `0xB` 恢复为收包状态 `0xC` 并清缓冲长度，以接收较后的普通帧。

这也解释了为何不能把短帧称为软件链路keepalive：它不会刷新普通接受路径的失联统计。可以维持或准备射频活动，是另一层效果，仍待实测。

## 五、独立恢复片段与核验

- `mode4_special_behavior.py`：独立的主生产条件、准备门限与接收拒绝行为模型；没有修改既有mode4 codec。
- `mode4_special_test.py` / `mode4_special_test_results.json`：实际通过 **2087条断言**，包括8种连接状态×256计数的边界、6个队列分别非空、其他入口门控、CC7边界，以及6段原始指令字节核对。
- 测试证明模型与静态条件及文件字节一致；不执行目标固件、不模拟整个DPPI/RADIO硬件，也不等于空口验证。

仍未确认：特殊帧真正的射频状态/功耗收益、全部异步入口下SHORTS位保留情况、并发队列变化、异常接收状态的全覆盖，以及厂商原始命名。后续最有价值的验证是已有镜像的局部原指令差分或只读状态/空口观测，而非修改原固件来试探。
