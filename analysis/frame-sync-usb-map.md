# Frame Sync：接收器 USB 时间基准与无线定时器

本轮已从原固件闭合一条 **USB SOF → 软件回调 → 无线 TIMER 相位校正** 的调用链。普通 HID IN 提交和完成回调是另一条路径：IN 完成回调只释放报告忙状态，没有写入无线定时器。这里的相位样本来自 SOF 事件被软件分发到应用回调时的 TIMER 捕获值，并非 USB 总线边沿的硬件直连捕获。

范围仅为官方接收器 1.20 `Suit1FWData__radio_radio.bin`。SHA-256：`f7a9bd6f51490bcceeaf0121775e2da3ef701a7a3218862956fb60dde2c52162`。复核原始 Thumb 指令、初始化数据和已保留 SVD；未运行 headless、未改 portable、未写设备，未新增原指令差分测试。[JSON证据](frame-sync-usb-map.json)保存42段原字节、各段hash、完整镜像与参考文件hash及28条调用边。

## 1. SOF 来源闭合

|阶段|准确位置|原指令/数据证据|
|---|---|---|
|USB控制器|设备`0E06F6B8`，config`0E07031C`|config+10为`2F700000`；API表`0E070350`|
|中断入口|`0E0664C4`|读取控制器`+014 & +018`；`E0664FC..4FE`检测bit3|
|SOF分支|`0E0669D8..69F6`|向`2F700014`写8清事件；读`2F700808`，UBFX bits8..21，存driver private+360；随后`r1=5,r2=0`调用`E064778`|
|事件入队|`E064778 → [controller.data+98] = E063145`|`E0633E4 → E064CA4`注册该回调；`E063144`向`23001C2C`调用`E06CBDC`，timeout=0|
|USB线程|`E063240`|从相同queue取事件；event5到`E0632A6`，仅USB context+2C==2时调用`E0631F0`|
|HID class回调|`E0631F0`|event5取class API+1C；表`E0710A0+1C`原值`E0640B9`|
|应用SOF回调|`E0640B8`|取HID ops+20并tailcall；第一组ops`23000420+20`原值`23026DE1`|
|无线计时捕获|`23026DEE / 23026DF0`|先向`5302805C`写1（CAPTURE7），然后直接BL `23022204`|

本地 Nordic SVD 标注 `GLOBAL_USBHSCORE0` 的 GINTSTS+014 bit3为 **Start of (micro)Frame**，DSTS+808 bits8..21为 **SOFFN**。因此“event5是SOF”同时有硬件寄存器与软件分发两类证据。[Zephyr UDC枚举](https://github.com/zephyrproject-rtos/zephyr/blob/main/include/zephyr/drivers/usb/udc.h)与[HID SOF桥接源码](https://github.com/zephyrproject-rtos/zephyr/blob/main/subsys/usb/device_next/class/usbd_hid.c)也与所见布局一致；这是语义交叉核对，不能据此认定固件采用当前main版本。

SOF不是直接从ISR调用`23026DE0`：它经过事件队列和USB线程。因而捕获包含软件分发延迟。官方[HID SOF回调说明](https://docs.zephyrproject.org/latest/doxygen/html/structhid__device__ops.html)同样提示这种回调有软硬件抖动；本次没有实测该抖动。

## 2. 无线 TIMER 的相位算法

`23026DE0`首先要求`byte[230071E4]!=0`。进入后，无论报告队列是否有数据、随后是否进入IN提交，都会先CAPTURE7并调用`23022204`。它不使用报告提交成功、IN完成时间或USB帧号作相位输入。

`23022204`主要动作：

- `u16[3230]==5`直接退出。启动/重同步状态由`3250/3256/3258/325A/325B/325C`等字节控制，不能把每个SOF都当作一次校正。
- `325A!=0`时，暂时关闭IRQ40，向NVIC `E000E284`写`0x100`清pending，再对**无线使用的同一个**`TIMER020_S`执行CLEAR、START，重新开IRQ；随后`325A=0,325B=1,325C=0,3264=0`。这是直接按SOF回调到达时刻重设定时器起点。
- `325B!=0`期间递增32位`3264`；带符号比较大于32后清`325B`、置`325C=1`，进入测量阶段。
- 测量需要`3250=0,3256=0,3258!=0,325A=0,325B=0,325C!=0`。读取`CC7=5302855C`，原无符号条件`(CC7-0x6E1)<=0x63E`，只接受**1761..3359**的样本。
- 有效样本累加到32位`3270`，样本数`3278`加1。原指令对count做带符号`>31`比较，再对sum做`ASR #5`；正常从0开始即32个有效样本求均值，不要求它们来自连续32次SOF。
- 均值目标为`0xA00=2560`，死区±31：均值≥2592则`CC0 += 32`；均值≤2528则`CC0 -= 32`；2529..2591不改。随后清sum/count。递增及加减使用原32位自然回绕语义。

原写入地址为`53028540`（CC0），不是软件延时计数。`23022D18`把TIMER SHORTS写1，SVD确认bit0是COMPARE0→CLEAR；已恢复的正常mode1/2/4 CC0处理分别在`23023D1C / 23022F72 / 23024A16`把CC0重设16000。由此可判定这里通过修改下一次比较/清零时刻修正无线周期相位，不能描述成永久改动晶振频率。

启动关联也可见：`23022008`依据`u16[323A]==1`设`3250`与`3258`；`23021EB8`在同条件下只置`325A=1`，把CLEAR/START留待SOF路径执行；其他情况自行CLEAR/START。完整上层开关来源由主任务另行追踪，本报告不把`323A`擅自命名为用户界面开关。

本文保持固件原始tick单位。实际timer时钟、USB全速帧/高速微帧频率、采样窗口与总线时刻的绝对微秒换算未在本报告闭合。

## 3. IN提交与完成

应用SOF回调在相位处理后，若USB状态不是3且第一报告环非空，则tailcall `23026948`；若环为空，调用`E06D5C8(queue=23002170, work=23002220, delay=(50,0))`安排工作。工作handler为`23026D29`，其主体`23026D28`最后同样进入`23026948`。

`23026D28`先最多21次写`5F9A2048=1`并读`5F9A2548`：当捕获值不在1..69，或队列0已有数据，即结束等待。SVD可将这两处明确识别为 **GLOBAL_TIMER130 CAPTURE2/CC2**，不是USB帧号寄存器。其timer启动/复位相对SOF的关系仍未闭合，不能把该等待直接说成“等USB SOF”。

实际提交链：

`23026948 → 23027188 → E064504 → device API+4(E064289) → E064288 → E063EE0 → E064AB4 → controller API+4(E065345) → E065344`

三个HID设备为`E06F6A4/E06F690/E06F67C`，报告长度8/16/8。`E064288`构造buffer；`E065344`将buffer放入endpoint FIFO并向控制器线程发送事件，返回0只是软件入队成功。控制器线程`E066D3C`经`E065734 → E065570`设置IN传输长度、端点控制并填FIFO。没有证据支持“提交函数返回0即PC已收到”。

完成链与SOF分离：

`E066D3C → E064798(event6) → E063144 → USB event thread E063240 → E063A80 → class API+10(E064145) → E064144 → HID ops+18(23026CD1)`

`23026CD0`只做：dev0的`6904`忙计数非零则减1；dev1清`6901/6909`；dev2清`6902/690A`。它没有捕获CC7、调整CC0或重启TIMER。

三组HID ops由`23026C58 → E06450C → E0641C4`注册；运行时位于`23000420/444/468`，原加载地址`E070C74`，每组36字节。+18均为IN完成`23026CD1`；+20仅dev0为SOF `23026DE1`，其他两组为0。这避免三个HID接口重复执行同一个相位校正。

`E0622BC`另属唤醒路径。它由`23026AD8`在USB状态3时调用，检查remote-wakeup能力/host许可/suspend位并调controller API+20=`E06521D`；该函数给驱动线程发`0x10`事件。它不是普通HID IN提交入口，也不直接校准无线相位。

## 4. 已证实与未闭合

**已证实到原字节层面：**SOF硬件状态位→event5→USB线程→HID SOF回调→捕获无线TIMER→起点重置/CC0微调；IN完成走event6并释放busy，校正函数不读取USB帧号。

**未闭合：**上电到USB配置完成的所有调度未执行验证（SOF mask使能原指令已在下节确认）；GLOBAL_TIMER130的基准关系；软件回调延迟分布；实际USB轮询到达与RF时隙的相位误差；传感器侧、鼠标侧到该接收器校正的端到端链。现有原指令测试曾在USB驱动边界停下或显式注入外部结果，不能作为真实USB完成/时序验证。本轮结论是固件机制证据，不是实机同步性能结论。

## 5. 补查：SOF mask、速度与微帧分频

**SOF mask使能已有原指令证据。**控制器使能函数`E065B84`成功完成端点配置后，`E065DC4`从`E065E88`加载常量`0x803C3808`，`E065DC6`写USB基址+18（GINTMSK）。bit3置1允许SOF中断；同函数随后设置全局中断使能和解除soft-disconnect。本结论是代码路径存在，不代表已在实机观察该路径执行。

**速度来自枚举结果，而非硬编码当前连接为高速。**`E066946`处理GINTSTS bit13 ENUMDONE；`E06695C..6972`读取DSTS bits1..2，将其保存在driver private+362的高两位。SVD定义0=HS、1/3=FS、2=LS。`E0650F0`读取该字段，0返回2，非0返回1；`E064BBC`为该getter的上层封装。USB事件线程`E063310..63338`将返回值是否为2转换为USB context+60 bit4，`E062244`读取此标记；接口ready回调`23026C3C`将结果写`230071E5`。因此固件存在运行时区分HS/非HS的路径，当前没有接收器，不能报告实际链路协商结果。

**已检查的SOF回调链没有软件“8个微帧取1个”分频。**`E0669D8..69F6`在每次处理SOF状态位时，保存SOFFN后直接发event5，没有检查`frame&7`、计数阈值或速度。`E063144`直接无等待put；`E063240`的event5只检查configured状态；`E0631F0`与`E0640B8`直接分发。队列`23001C2C`的初始化字段为msgsize12、capacity256、buffer`23014240..23014E40`。没有看到刻意合并或抽取八分之一事件；队列拥塞、IRQ延迟或配置状态可能影响实际到达，不能据此保证每个总线事件都被软件处理。

SOF有可能是frame或microframe，物理频率取决于实际协商速度和控制器运行状态。本报告可以排除**这条已追踪软件链里的显式1/8分频**，不能仅据静态代码宣称实测回调125µs或1ms。`23022204`按CC7范围筛选相位样本属于测量窗口过滤，也不能混称为USB回调分频。

## 6. 补查：GLOBAL_TIMER130的起点仍是明确缺口

对五份接收器叶级镜像（radio、application、sysctrl、sec、sec_rec）扫描secure/nonsecure TIMER130窗口内的32位地址字，并检查保留radio/application反汇编：完整`5F9A2000`原字仅出现在radio文件偏移`0x74F8`，映射`23026D5C`，正是报告worker的literal；其余镜像没有完整的TIMER130基址字。sec镜像另有文件偏移`0x24ADC`的32位字`0x4F9A2D8D`落在扫描范围，但尚未证明它是外设指针或有效访问，不能据此推定启动/复位。保留radio/application导出未发现TIMER130 START/CLEAR写入，也未发现构造`5F9A/4F9A`高半地址的明确指令。每份镜像的大小、hash与扫描命中已追加到JSON。

这个结果只限定“当前镜像和保留导出中没有找到初始化来源”，**不证明TIMER130未运行或不存在初始化**：间接计算的外设地址、其他启动代码、跨核配置等仍可能未被此次方法覆盖。因此继续保留`5F9A2048/2548`为“捕获TIMER130 CC2并做短等待”的确定行为；其START/CLEAR与SOF、RF周期或系统时基的关系尚未闭合，不能将其直接命名为USB相位计时器。
