# 握手状态转换：原指令差分与可编译 C

本轮在既有逐字节握手契约上恢复了两端有限状态分支。不是完整无线状态机，也没有运行实机固件。

## 接收器 0x230223f0

新增 `dongle_handshake_transition.py`，以224字节slot快照为状态。原指令入口及所有实际调用的辅助函数由 `EmulateHandshakeTransition.java` 执行；没有替换指令或跳过callee。640组输出全部一致：状态0接受175组/拒绝113组，状态2接受140组/拒绝20组，状态3完成77组/拒绝19组，其他状态拒绝96组。完整数据见 `handshake-transition-original.jsonl` 及 `handshake-transition-comparison.json`。

恢复的具体规则：

- 接收头bit7非零、长度不等于11、命令与子状态不匹配时返回0，不生成回复。
- 状态0的身份过滤只比较incoming byte6/7；pending为0或已存首字为FFFF时绕过该比较。不能把4字节身份更新误称为4字节身份验证。
- 两个全局状态均不大于2时使用主能力掩码，否则使用备用掩码；交集模式优先8、4、1、2。
- 对端flag7写入发生在能力交集判断之前，因此“返回0”不保证完全没有状态变化。
- 身份4字节同时写为原字节和两对交换字节布局；所选模式写全局状态。
- 状态2收到0x14，先把byte4存为16位局部值，再构造0x15。selector为0/1写8字节、2写6字节、3写5字节；其他16位值完全保留原数据区，但仍推进状态和序号。已有高层codec仅接受0..3，那是分析接口约束，不是固件拒绝规则。
- 生成0x13/0x15后推进序号，写计数字段0x40000，子状态分别变为2/3。该计数字段此处不换算为绝对时间。
- 状态3收到0x16且pending为0，清计数字段，子状态变为6，返回2。pending非零的队列/通知路径未纳入这次原指令运行。

比较覆盖全部224字节、全局选定模式及返回值，不只比较报文。测试输入包括slot0/1、主/备用能力、0..3及越界selector、拒绝输入和旧缓冲随机尾部；不是穷举整个固件状态空间。

## 鼠标 0x230227b8

新增 `mouse_handshake_transition.py`，模拟软件radio状态0x14下的RX处理。`EmulateMouseHandshake.java`从实际函数入口运行原指令和实际辅助函数，256组全部一致。

三种回复0x12/0x14/0x16分别有64组成功输入；其余64组为CRC失败、头bit6置位、错误长度、错误命令或事件参数不匹配。51组返回搜索状态0x13，13组因事件不匹配保持0x14。两端共六种握手报文现在均有至少一个原始生产路径的软件执行依据。

比较全部992字节RAM窗口及15个选定寄存器字。成功回复的状态转换、sequence、频道掩码/频点复制、接收的mode和selector、局部计数与TXEN订阅值均由这些字节覆盖。

限制：测试均令配对标志为0；未运行TX完成状态0x16和终态0x17的初始化。MMIO区域是普通模拟内存，CRCOK为给定输入，不模拟真实CRC、事件清除语义、定时器或DPPI。上述验证不能证明实机状态同步或RF时序。

## 可编译的恢复源码

`../recovered-code/portable/`内的C模块通过Clang C11严格警告构建。`verify_portable_handshake.py`直接将C输出与保存的原指令结果对照，**1,024组通过**，包含先前首报文128组、新接收器640组及鼠标256组。Python模型的结果未作为C验证的最终oracle。

源码是重新编写的恢复实现，类型与名称为分析命名。仍缺通知、全部生命周期、硬件驱动及完整业务栈；不能据此称完整原始源码已取得。
