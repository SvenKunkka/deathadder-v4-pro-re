# 接收器通知管理线程与连接消息生产者

恢复连接/断连通知的消费循环 `230253DC`，以及连接事件生产者 `2302546C`。它接入已有的USB报告队列、无线B1发送、timer启动/停止和消息队列实现。**这些是软件队列操作，没有执行USB或RF传输。**

## 具体行为

|输入|恢复行为|
|---|---|
|通知事件1|按peer低8位决定移位，更新连接位图`6590`，`65E6=5`；非零peer随后回到循环|
|事件1、peer0|以参数`(1,1)`更新`2C80`并排入USB连接报告；向无线peer0排入6字节B1状态及校验；按模式条件排入USB模式报告；停止`1A30`，最后清零完整32位`65E2`|
|事件2、peer0且`65E2`低16位为0|启动`1A30`，延时传入值2000000、周期0；清`65DE`半字，置`65E2`低半字为4；不额外推断时间单位|
|断连定时器到期回调|清连接位图`6590`，置完整`65E2=0x50000`，调用连接状态辅助函数`(1,0)`，排入USB断开报告并清相关发送队列计数|
|其他事件/条件|回到下一循环头；事件5在这里没有持久化处理|
|连接事件生产者|将事件1、8字节参数及24字节原栈尾部组成36字节消息；入队失败则purge后重试；真实CPU边界照常保留|

连接调用中的第二个参数由汇编确认仍是1；自动反编译省略了它。停止定时器后的`65E2`清零是32位写入，包含上半字，已保留。USB启用标志、环队列满、无线队列不足等条件保留原行为；没有为顺利发送而增加重试或清队列。

## 验证证据

6类各1,024组：连接状态辅助函数、模式通知selector2、出队后通知分派、完整一次通知循环、连接事件生产者、实际断连到期回调。合计6,144组，945,483条原指令执行；4,096完整函数返回、1,859下一循环头、173 CPU请求边界、16人工stop回调边界。全部通过。

比较128KiB RAM、九个外设/标识窗口、消息输出、BASEPRI和待处理入口/参数。覆盖USB启用/禁用、队列满与坏索引重置、无线队列满、peer移位边界、连接模式、活动timer及等待线程。原指令记录从前4,096组延续新增1,024组生产者及1,024组实际到期回调，旧记录保留，无重复加计。[原指令结果](receiver-notification-runtime-comparison.json) · [原字节与摘要](receiver-notification-runtime-exact.json)

另128轮连续连接/断连通过：256条消息从真实生产者经过通知队列与管理消费者，128次timer启动和128次停止；96条USB报告入队、160次禁用或满队列丢弃；120条B1消息入队、8次空间不足拒绝。独立检查B1两片载荷、校验、序号以及USB环队列模型。[连续结果](receiver-notification-continuous-comparison.json)。

连续测试显式提供32次USB队列消费及210次无线队列pop；它们不是实际传输。BASEPRI为0x80，未自动执行线程切换。24字节旧栈尾部由测试明确提供且逐字节检查，没有伪造为零。这些组件用例不增加原指令输入数。

固件静态初始化表为`1A30`注册了`230255B9`（Thumb地址），stop回调为0，原始56字节和文件偏移已写入证据记录。不能据此排除后续动态修改。到期回调的1,024组验证直接执行其原指令，不等于RTC自动触发或通用timer到期框架已完成。
