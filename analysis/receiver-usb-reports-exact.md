# 接收器 USB 报告回调恢复（官方 1.20，第57阶段）

已恢复工作回调 `23026D28` 及其报告处理体 `23026948`，新增 [receiver_usb_reports.c](../recovered-code/portable/receiver_usb_reports.c) 和 [接口说明](../recovered-code/portable/receiver_usb_reports.h)。这是根据固件指令重写的 C，不是厂商原始源代码。

## 行为与来源

- 包装回调向 `5F9A2048` 写1，并检查 `5F9A2548` 和第一组队列读写指针，最多循环21次；外设窗口在本次验证中是静态快照，未确定其物理时序效果。
- `230071E4` 为0时不提交报告。三组4槽环形队列的读指针在 `6834..6836`、写指针在 `6838..683A`，生产者保留一个空槽。
- 类别1→环0→8字节，类别4→环1→16字节，类别2→环2→8字节。环0使用 `1E60/1E80` 双缓冲，环1使用 `1E40`，环2使用 `1E20`。
- 环0只在忙计数≤1时提交，先增加计数；成功推进读指针并将切换字设为 `1-原值`，失败且计数非零时减1。
- 环1、2只在各自忙字节为0时提交，先置忙1和状态3；成功推进读指针，失败清除这两个字段。成功后忙状态仍可能依赖实际 USB 完成回调。
- 读指针异常且确实进入对应队列分支时，会清除三组读写指针；没有清除相邻第4字节。8字节报告不清除缓冲区其余字节。
- 实际调用链为 `23027188 → 0E064504 → 设备虚表 → 0E064288`。三个设备结构和虚表原字节已保存在 [证据清单](receiver-usb-reports-exact.json)。

## 验证结果

[原指令差分结果](receiver-usb-reports-comparison.json)：2,048组输入、159,220条原始指令。比较全部128KiB RAM、4KiB辅助外设快照、实际驱动入口的参数和报告字节。280组无需进入驱动即返回；442组停在真实驱动入口；1,326组在明确提供外部驱动返回值/副作用后完成回调。最后一类不能视为原驱动执行成功。

[连续组件结果](receiver-usb-reports-continuous-comparison.json)：64轮、576份报告入队，192次满队列拒绝；192次显式失败后的重试保持报告内容一致。测试显式提供完成状态及调用次序，未模拟真实工作线程调度或 USB 完成中断。

默认接口不提供驱动 hook，会在 `0E064288` 停下，返回真实调用参数。只有调用方明确提供 hook 时才继续执行回调后半段。该 hook 是环境输入接口，不是 USB 驱动替代实现。

## 尚未完成
